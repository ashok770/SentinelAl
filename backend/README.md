# SentinelAI Backend

## Demo Security Activity Data Engine

**DISCLAIMER**: Current demo activity is synthetic and is used only to demonstrate the SentinelAI analyst workflow. It is not a trained ML prediction.

### Purpose
The demo activity data provides a realistic, deterministic layer of synthetic security events for an enterprise environment. It allows us to build and demonstrate the complete SentinelAI product workflow (dashboards, alerts, investigations) before integrating the real CERT insider-threat dataset and trained ML models. 

This demo data layer is designed to be easily replaced by the real Data Science/ML pipeline in the future without changing the frontend consumers.

### Seed Command
You can generate a deterministic dataset (mostly normal activity plus a few suspicious behavioral patterns) by running:
```bash
npm run seed:demo
```
This command clears existing demo data and inserts 10 synthetic users and approximately 780 activity events spanning a multi-day range.

### Behavioral Analysis Engine
The Behavioral Analysis Engine evaluates synthetic user activity against a historical behavioral baseline. **This uses deterministic behavioral rules over synthetic activity data. It is an interim intelligence layer and will later be replaced or augmented by the trained Data Science/ML pipeline.** 

#### Baseline
The baseline calculates typical behaviors such as average daily file access and data transfer over the user's historical events.

#### Signals and Thresholds
The analysis engine dynamically evaluates the latest 24 hours of activity (or a specified window) to extract the following signals:
- **UNUSUAL_LOGIN_TIME**: Detects login activity outside the user's `normalWorkingHours`.
- **NEW_DEVICE**: Detects activity from a device not present in the user's `normalDevices`.
- **ABNORMAL_FILE_ACCESS**: Detects file access volume exceeding 3x the baseline average (minimum 10).
- **ABNORMAL_DATA_TRANSFER**: Detects transfer volume exceeding 3x the baseline average (minimum 100MB).
- **SENSITIVE_RESOURCE_ACCESS**: Detects any sensitive resource interaction.

### Risk Scoring Engine
The Risk Scoring Engine consumes the signals generated by the Behavioral Analysis Engine and calculates a deterministic risk score and severity band for the user. **The current Risk Scoring Engine is a deterministic demonstration layer built on behavioral signals from synthetic activity data. It is not a trained machine-learning model.**

#### Signal Weights
- `UNUSUAL_LOGIN_TIME`: +20
- `NEW_DEVICE`: +20
- `ABNORMAL_FILE_ACCESS`: +25
- `ABNORMAL_DATA_TRANSFER`: +25
- `SENSITIVE_RESOURCE_ACCESS`: +10

*The final risk score is safely clamped between 0 and 100.*

#### Severity Thresholds
- **0–24**: LOW
- **25–49**: MEDIUM
- **50–74**: HIGH
- **75–100**: CRITICAL

### Alert Engine
The Alert Engine determines if a calculated risk score warrants analyst attention. Alerts are persisted to MongoDB to provide a static record of an anomaly that analysts can investigate. 

#### Creation Threshold
- Alerts are strictly created ONLY when the Risk Scoring Engine returns a risk of **50 or higher (HIGH or CRITICAL)**. LOW and MEDIUM risks do not generate alerts.

#### Deduplication
- Alerts use a deterministic compound index deduplication strategy (`userId` + `analysisStart` + `analysisEnd`). Re-evaluating the exact same user for the exact same window will return the existing alert rather than duplicating.

#### Alert Lifecycle
- Alerts default to **OPEN**.
- Analysts can transition alerts to **ACKNOWLEDGED**, setting the `acknowledgedAt` timestamp.
- Analysts can transition alerts to **RESOLVED**, setting the `resolvedAt` timestamp. (Invalid backward transitions, such as RESOLVED to ACKNOWLEDGED, are strictly rejected).

### Investigation Intelligence
The Investigation Intelligence layer aggregates context across the entire stack into a single payload for an analyst reviewing an alert. It bridges:
1. **The Alert**: Metadata and status.
2. **The User**: Sanitized user details (role, department, normal working hours).
3. **The Risk & Behavior**: The exact severity, contributing signals, and behavioral baseline that triggered the alert.
4. **The Timeline**: A chronologically sorted subset of actual Activity records from the exact window of analysis.
5. **The Evidence**: A deterministic summary directly mapped from the active signals.

*Note on Annotations*: Due to the deterministic nature of the demo Behavioral Analysis (which evaluates aggregates over windows), exact event-level attribution (e.g. knowing exactly *which* data transfer breached the threshold) is provided purely as a best-effort heuristic in the timeline. If the system is uncertain, it safely provides no annotations rather than inventing false attribution.

### Dashboard Aggregation
The Dashboard Aggregation layer serves as the unified interface for the frontend application to present summary metrics, risk distribution, recent alert history, and time-series risk trends.

* **Purpose**: This service aggregates data from the `RiskScoringService` and `AlertService` into frontend-optimized payloads.
* **Current Risk**: The risk summaries and distributions calculate the *live*, current risk of all DemoUsers by analyzing their latest activity baselines, rather than relying solely on older, persisted Alert snapshot severities.
* **Alert Semantics**: The dashboard distinguishes between `OPEN`, `ACKNOWLEDGED`, and `RESOLVED` alerts when providing counts to analysts, focusing predominantly on `OPEN` alert queues.
* **Trend Semantics**: The trend calculates historical Alert volume deterministically grouped by the day they were triggered (`createdAt`). It does not interpolate fabricated dates for days where no alerts were generated.

**DISCLAIMER**: The dashboard APIs are aggregation APIs over the current deterministic demo intelligence layer. They do not represent trained machine-learning predictions.

#### API Endpoints (Protected by JWT)
- `GET /api/v1/dashboard`: Fetch the complete aggregated dashboard overview.
- `GET /api/v1/dashboard/summary`: Fetch high-level user and alert counts.
- `GET /api/v1/dashboard/risk-distribution`: Fetch the exact count of users mapped to `LOW`, `MEDIUM`, `HIGH`, and `CRITICAL` risk.
- `GET /api/v1/dashboard/recent-alerts?limit=10`: Fetch a chronological queue of the latest alerts.
- `GET /api/v1/dashboard/risk-trend`: Fetch a deterministic time-series ledger of historical alerts.
- `GET /api/v1/investigations/alerts/:alertId/context`: Fetch the full intelligence context for an alert.
- `GET /api/v1/alerts`: Fetch persisted alerts (Optional filters: `status`, `severity`, `userId`).
- `GET /api/v1/alerts/:alertId`: Fetch a specific alert.
- `POST /api/v1/alerts/evaluate`: Evaluate risk for a specific user and analysis window, returning a persisted alert if HIGH/CRITICAL.
- `PATCH /api/v1/alerts/:alertId/acknowledge`: Acknowledge an alert.
- `PATCH /api/v1/alerts/:alertId/resolve`: Resolve an alert.
- `GET /api/v1/risk`: Fetch risk assessments for all demo users.
- `GET /api/v1/risk/users/:userId`: Fetch risk assessment for a specific demo user.
- `GET /api/v1/analysis`: Fetch analysis summaries for all demo users.
- `GET /api/v1/analysis/users/:userId`: Fetch behavioral analysis for a specific demo user.
- `GET /api/v1/activity`: Fetch activities.
- `GET /api/v1/activity/users`: Fetch all demo users.
- `GET /api/v1/activity/users/:userId`: Fetch activities for a specific demo user.
